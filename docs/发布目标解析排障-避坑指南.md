# 发布目标解析排障 · 避坑指南

> 配套《发布目标解析排障-SOP》使用。版本 v1.0（2026-10-14）
> 每条都是实战踩过的坑，标注了「坑象 / 真相 / 对策」。

---

## 一、认知坑（最贵的三条）

### 坑 1：把「机器级绑定」当成平台账号关系
- **坑象**：发布总被路由到某个陌生应用，以为平台把自己账号和别人的应用绑死了。
- **真相**：绑定信息在**本地**（工作区 `.workbuddy/applications.yaml` + 部署历史 JSON），不在平台账号。账号后台为空 ≠ 本地记录为空。
- **对策**：永远先用「账号后台真实列表」校验本地记录，矛盾处即毒源。

### 坑 2：以为发布失败是网络/临时故障，反复重试
- **坑象**：「暂时无法连接原发布环境」→ 以为重试几次就好。
- **真相**：这是**平台护栏**——目标 appId 的 sandbox 建在旧账号环境，本账号连不上，平台选择停止而不是换链接（保护既有分享链接）。重试一万次结果一样，且每次「重试成功」都可能覆盖别人的线上内容（本次事故中真实发生过两次）。
- **对策**：出现该文案立即停手，进 SOP 流程，不要重试。

### 坑 3：发布成功就收工
- **坑象**：返回 `verified: true` 就认为完事。
- **真相**：verified 只证明「发到了被解析到的目标」，不证明「目标正确」。
- **对策**：每次发布后 30 秒内探针：新链接内容对不对、旧链接动没动。

## 二、工具坑（假阴性陷阱）

### 坑 4：BSD grep 不支持 `\|` 交替
- **坑象**：`grep "a\|b" file` 无输出，误判「没有匹配」。
- **真相**：macOS 自带 BSD grep 的 `\|` 不是正则交替（需 `-E` 或用 ripgrep）。
- **对策**：排查关键证据一律用 **Grep 工具（ripgrep）**或 `grep -E`；「无输出」至少换一种工具复验一次再下结论。

### 坑 5：日志被轮换，历史样本缺失
- **坑象**：想找「首次创建应用」的日志作参照，发现 9 月的日志已没了。
- **真相**：`~/.workbuddy/logs/sites/` 按日切割会清理旧文件。
- **对策**：重要排查结论当场写进工作日志，别指望日后回看日志。

### 坑 6：多行/复杂命令被沙箱策略拦截时报错信息费解
- **坑象**：`cmd decisionRecord missing actual resource subject`。
- **真相**：管道/重定向/多语句组合触发了决策记录缺失。
- **对策**：拆成单步命令顺序执行；复杂操作用脚本文件再运行。

## 三、操作坑（修复期的手脚）

### 坑 7：修 manifest 时把别的应用信息也删了
- **坑象**：清单里有多条记录，图省事整文件清空。
- **真相**：manifest 是**按工作区**读的，别的 workspace 的清单管不到本项目，但**同一文件里的其他条目可能是别人的活路**。
- **对策**：只删/只改毒条目；本例正确修法是把唯一条目清空为 `applications: []`（该文件本就只此一条）。

### 坑 8：删除污染的历史记录
- **坑象**：把绑错 appId 的历史 JSON 直接 `rm`。
- **真相**：记录是「按目录直查」的输入，删除能让直查落空（也能达到隔离效果），但**丢了证据**；且万一删错，发布工具的目录索引可能异常。
- **对策**：**改名**为 `*.stale-other-account`（保留内容、退出索引），日志里注明「切勿改回」。

### 坑 9：修复后手动往 manifest 写新 appId
- **坑象**：修完怕工具找不到应用，自己补一条 `locator: wbapp_xxx`。
- **真相**：无记录时发布工具会自动创建并自动写回 manifest；手写若写错反而制造新毒源。
- **对策**：修完就发布，让工具自己写。

### 坑 10：入口页文件名想当然
- **坑象**：发布时传了 `entryHtml=nav.html`，以为根路径就会打开 nav.html。
- **真相**：平台静态服务器**根路径固定服务 `index.html`**，entryHtml 只影响「应用卡片点击打开哪页」。首页不是 index.html 就会开错门。
- **对策**：应用首页必须叫 `index.html`；其他页面任意命名（如 course.html），改文件名时同步全文检索交叉引用（`grep -rn "nav.html"`）。

### 坑 11：改完不更新 build 戳
- **坑象**：线上核验时无法判断「到底发没发上去」，浏览器缓存还会骗人。
- **真相**：`<meta name="build">` 是唯一可靠的线上版本锚点。
- **对策**：每次改发布目录文件必更新 build 戳（`NAV-YYYYMMDD-HHMM`），核验先看戳。

## 四、验证坑（收尾环节）

### 坑 12：只验新链接不验旧链接
- **坑象**：新应用对了就收工，没看旧应用有没有被顺手动掉。
- **对策**：成对探针：新链接（内容+build 戳）与旧链接（build 戳/标题原样）都要看，写入日志。

### 坑 13：用「无输出」证明干净
- **坑象**：`grep` 没匹配就宣布无残留。
- **真相**：见坑 4；另外残留可能在二进制/压缩文件里。
- **对策**：关键「无残留」断言用两种工具或加 `-c` 计数复核。

## 五、一句话清单（贴电脑边）

1. 账号后台列表是最高真相，本地记录与它矛盾 = 有毒。
2. 「无法连接原发布环境」是护栏，停手排查，别重试。
3. 发布成功 ≠ 目标正确，成对探针新旧链接。
4. 修本地状态只改毒条目，先备份，历史记录改名不删除。
5. 修复让工具自己写回 manifest。
6. 应用首页必须是 index.html，交叉引用全文查。
7. build 戳每次必更，它是线上核验的锚。
8. macOS 排查用 ripgrep，「无输出」换工具复验。
9. 每个改动进日志，回滚命令当场写好。
10. 账号-应用绑定表在平台侧，本机证据链到此为止，拿齐四层证据再升级。
