# 发布目标解析排障 SOP（跨项目可复用）

> 版本：v1.0（2026-10-14 蒸馏）
> 来源：铸铭问鼎论英雄-大篆训练营项目发布被劫持事件的完整排查实录
> 适用：任何「发布/部署到云端时目标应用不符合预期」的问题

---

## 0. 适用范围与两类症状

**适用**：发布动作**没有报错却发到了别处**，或**发布被平台拒绝但原因像雾里看花**的场景。

- **症状 A（静默劫持）**：发布返回成功，但打开链接是**别的项目/别人的页面**，或历史记录里 shareLink 指向陌生域名。
- **症状 B（幽灵拒绝）**：发布被拒，平台回复「暂时无法连接原发布环境…为避免更换分享链接，本次发布已停止」，但你从未见过那个「原发布环境」。

## 1. 总原则（先背下来再动手）

1. **先证据后修复**：没拿到「毒源在哪一层」的铁证前，不动任何配置文件。
2. **账号侧真相优先**：用户在自己账号后台看到的真实列表，高于本地任何记录。本地状态可能与账号实际不符（旧账号残留、机器迁移）。
3. **单点修复**：一次只改一个文件/一条记录，改完立刻验证，绝不「顺手清理」。
4. **全程可回滚**：每个修改前先 `cp` 留 `.bak`；每个改动写进工作日志。
5. **发布后必须探针**：发布成功 ≠ 发布正确。立刻核验新链接内容 + 旧链接未动。

## 2. 证据链四层模型（由外到内）

```
L1 账号侧：用户在平台后台看到的真实应用列表（截图/口述）
L2 平台侧：发布返回体/API 回复里 appId 的真实身份（名字、创建时间）
L3 本地状态：部署历史记录 + 工作区 manifest 清单
L4 服务端行为：官方文档/技能说明里「目标解析」的规则描述
```

**矛盾即线索**：L1（账号空）与 L2（appId 有主）矛盾 ⇒ 绑定信息不是来自账号，而是来自本地（L3）。这是本类问题最高频的根因形态。

## 3. 排查步骤（S0 → S6）

### S0 固定现场

- 记录：发布目录、domainPrefix 参数、发布时间、完整报错原文。
- 备份工作区 `.workbuddy/` 与 `~/.workbuddy/cloudstudio-deploy-history/`（只读用途，先别改）。

### S1 拿账号侧真相（L1）

- 请用户在「设置—数据管理—已发布应用」截图。**空列表 = 强约束**：任何把发布路由到「已有应用」的本地记录都是脏数据。
- 若用户不便截图，至少确认：本账号是否新建过应用。

### S2 比对 appId 真实身份（L2）

- 从发布日志/返回体提取被路由到的 `appId` 与 `shareLink`。
- 访问旧 shareLink 看实际内容；从平台回复（错误信息、应用名）确认该 appId 的主人/创建时间/项目名。
- **判读**：appId 名字与当前项目无关 ⇒ 存在历史绑定劫持。

### S3 查部署历史记录（L3-a）

```bash
ls -lt ~/.workbuddy/cloudstudio-deploy-history/          # 看有哪些 appId/sandbox/链接
cat ~/.workbuddy/cloudstudio-deploy-history/<对应.json>   # 看 workspacePath 指向哪个目录
```

- **判读**：历史记录按**目录**直查——当前发布目录若在历史里有记录，发布目标会被它直接命中（绕过 manifest）。
- 发现「本项目的目录」绑着「别人的 appId」⇒ 毒源之一。

### S4 查工作区 manifest（L3-b）

```bash
cat <发布目录的上层工作区>/.workbuddy/applications.yaml
```

- 工作区 = 你打开项目时的工作目录（不是发布目录本身），找它上层带 `.workbuddy/` 的那一级。
- **判读**：`applications:` 列表里出现**与本工作区无关的 locator（appId）** ⇒ 毒源之二。
- manifest 回退规则（实证）：发布请求未显式指定应用时，若历史目录直查未命中，则**回退读 manifest 列表最后一条**（`entries=1, requested=<none>` 日志字样）。

### S5 确认服务端规则（L4）

- 读发布技能的 SKILL.md：确认「发布 always an overwrite」「无参数可在已有应用旁新建」。
- 结论形态：**无记录 ⇒ 自动创建第一个应用；有记录 ⇒ 覆盖它**。所以修复方向永远是「拆掉错误记录」，而不是「找个参数绕过去」。

### S6 修复（按证据单点执行）

| 毒源 | 修复动作 | 回滚 |
| --- | --- | --- |
| manifest 错绑条目 | 备份后清空为 `applications: []` | `cp xxx.bak applications.yaml` |
| 部署历史里本目录绑错 appId | **改名**为 `<原文件名>.stale-other-account`（不删除，保留证据） | 改回原名 |
| 历史记录与本项目无关但 appId 正确 | 不动 | — |

修复后**不要手动往 manifest 写新 appId**——发布成功后工具会自己写入正确的。

### S7 验证闭环

1. 重新发布，确认返回的 sandbox/shareLink 与旧的完全不同。
2. 探针新链接：内容确为本项目、build 戳/资源可达。
3. 探针旧链接：仍是原项目、未被覆盖。
4. 复查 manifest：已自动写入新 appId。

## 4. 修复矩阵速查

| 现象 | 最可能毒源 | 动作 |
| --- | --- | --- |
| 发成了别人的页面 | 历史目录直查 / manifest tail | S3+S4 |
| 「无法连接原发布环境」 | 路由到的 appId 属旧账号（其 sandbox 本机/本账号连不上） | 同上；平台拒绝是护栏，不是故障 |
| 账号空但发布说「已有应用」 | 本地 manifest 或历史记录 | S3+S4 |
| 修完还是老链接 | 还有第二层毒源没拆 | 回 S3/S4 逐层复查 |
| 根路径打开的页面不对 | 静态服务器根路径固定服务 index.html | 保证应用首页文件名 = index.html |

## 5. 升级路径

S1-S7 走完仍异常：把四层证据（账号截图、日志中 resolveDeployApplication 行、manifest 内容、历史 JSON）打包，交平台支持人工核查账号-应用绑定表——那是本机不可见的最后一层。
